Recommendations (not applied — judgement calls or larger work)

Medium O(n²) date maths in header rendering

The month/week header builders call colToDate(c) inside loops over all columns; colToDate itself walks from projectStart each call. With a 2-year+ window (500+ columns) that's >100k date iterations per render. Works fine today, but will degrade as the window grows. Fix: walk a single date cursor once per render (O(n)), or memoise col→date in an array rebuilt when the anchor changes.

Medium Firestore backups grow without bound

writeBackup() is nicely throttled (min interval between auto backups) but nothing ever deletes old backup docs, and rules forbid client deletes (allow delete: if false). Storage and read costs grow forever. Fix: a scheduled Cloud Function or TTL policy on the backups subcollection, or keep-last-N pruning done server-side.

Medium Accessibility is minimal

Zero aria-*/role attributes in the app; all core interactions (create/move/resize blocks, milestones, reorder) are mouse-drag only with no keyboard path; several controls are colour-only (tag colours, block colours). If accessibility matters for your audience, this is the largest gap. Quick wins: aria-label on icon-only buttons (⠿ handles, × removes), role="menu" on the context menu, focus trapping in the project picker.

Low No SRI hashes on CDN scripts

Firebase compat SDKs and Sortable are loaded from CDNs without integrity/crossorigin attributes. A compromised CDN could inject code with full access to the Firestore session. Adding SRI hashes is a one-line change per script tag (pin the exact versions you already use).

Low Seven top-level document listeners could be consolidated

There are 4 separate document mousemove and 3 mouseup top-level handlers (pan, block create-drag, milestone create/drag, etc.). No leak — all dynamic listeners were verified to have matching removals — but a single dispatcher per event would make interaction order explicit and debugging easier.

Low Duplicate CSS selectors defined in two places

Nine selectors (e.g. .table-view, .combined-name-cell, .combined-meta, .block-table td) appear twice in different stylesheet regions with different properties. They merge as intended today, but it's easy to edit one and be surprised by the other. Worth consolidating when next touching those areas.

Low Rules don't deep-validate newer fields

firestore.rules checks milestones is a list (≤500) and tagColors is a map, but not item shapes/value types (client-side sanitizeState does re-clean everything on read, which mitigates this). If you ever open access beyond the two allow-listed emails, tighten the rules first.

Low Inline onclick= handlers & single-file architecture

Seven functions are wired via inline HTML attributes (all verified to exist). Combined with the single ~200KB HTML file, this is a deliberate and coherent style — but if the app keeps growing, a light build step (split CSS/JS, ES modules, minify) would improve maintainability and enable caching.

What's in good shape

  • No XSS found:
  • all user content (labels, tags, names) rendered via textContent; every innerHTML interpolation carries only numbers or app-constant strings; the tag datalist XSS was already fixed with a comment.
  • No listener leaks:
  • every dynamically-registered document/window listener has a verified matching removeEventListener; Sortable instances are destroyed each render.
  • Robust sync design:
  • debounced saves, echo prevention via _clientId, deferred remote-apply while UI is busy, throttled backups, IndexedDB fallback, and defensive sanitizeState on every load path.
  • Clean code hygiene:
  • no var, no stray console.log/debugger, only 3 intentional == null idioms, thoughtful comments explaining non-obvious decisions (object identity in drags, rAF-batched render, weekday-column model).
